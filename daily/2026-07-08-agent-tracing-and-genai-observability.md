## why read today

你前面已经补过不少“怎么把 Agent 跑起来”的材料：工具调用、MCP、严格 schema、会话、handoff、Python 工程化。下一步最容易卡住的，不是“再学一个框架”，而是开始进入你熟悉但又会在 Agent 语境里变形的老问题：

- 一次请求为什么慢，到底慢在模型、工具、重试，还是状态流转？
- 一个结果为什么错，到底是提示词问题、工具参数问题，还是中间某一步上下文污染？
- 上线后用户说“偶尔不对”，你怎么把这种模糊反馈沉淀成可复现、可归因、可验证的工程证据？

这正好是你这种背景最该补的一课。你过去 10 年做 Java / Spring / IoT 集成 / ToB 交付，真正决定项目成败的从来不只是“功能有没有”，而是链路能不能看清、日志能不能对上、异常能不能定位、现场问题能不能回放。Agent 工程只是把这套要求重新搬到了模型调用、工具执行、handoff 和 token 消耗这条新链路上。

今天这两篇材料放在一起读，价值很高：

- OpenAI Agents SDK 文档告诉你：一个 Agent runtime 默认已经把哪些关键步骤包装成 trace / span，以及什么时候需要手工 `flush_traces()`。
- OpenTelemetry 官方博客告诉你：这些 GenAI 事件如果想跨框架、跨平台、跨团队地进入统一观测体系，应该用什么语义约定描述。

也就是说，第一篇回答“你在代码里怎么记账”，第二篇回答“你把账记出来之后，行业里怎么统一看账”。

## original-text translation

OpenAI Agents SDK 这篇 tracing 文档的核心意思很直接：**trace 不是额外插件，而是 agent 运行时的一等公民。** SDK 默认就会把一次 `Runner.run()` 包成完整 trace，再把 agent 执行、LLM 生成、函数工具调用、guardrail、handoff、音频输入输出这些步骤分别包成 span。这样做的意义，不是为了让页面上多一张漂亮链路图，而是为了把原本“糊成一团”的 Agent 执行过程拆成可以逐层定位的结构化事件。

文档还特别提醒了一个很工程化的细节：默认的 `BatchTraceProcessor` 是后台批量导出的。对长时间运行的 worker、Celery 任务、RQ 任务或 FastAPI 后台任务来说，trace 通常会自动发出去，但不保证每个任务一结束你立刻就在控制台或平台里看到。如果你在一个工作单元结束时就需要“现在必须落库、必须看见”，那就应该在 trace 结束后显式调用 `flush_traces()`。这和你过去做企业集成时“日志已经写了”和“日志此刻已经可查”之间的差别很像，前者是写入行为，后者才是交付可观测性。

OpenTelemetry 这篇官方博客则是在更上层讲同一件事：**GenAI 系统不是不能观测，而是需要统一语义后才真正可观测。** 文章强调，GenAI 语义约定把模型名、输入输出 token 数、结束原因，以及在允许采集内容时的 prompt、回复、工具调用和工具结果，都变成统一字段。这样一来，Agent 的行为就不再只是某家平台里的一堆私有日志，而可以进入标准化的 traces、metrics、events 体系。

博客里另一个非常重要的提醒是“默认不要采集全部内容”。默认情况下，只记录模型名、token 数、时延等元数据，不自动记录 prompt 内容和工具参数，因为这些数据经常带敏感信息。只有在明确选择打开内容采集时，才会把 system prompt、消息、工具 schema、工具参数和工具结果写进 span 属性里。换句话说，Agent observability 不是“能记多少记多少”，而是“先把字段模型和安全边界定清楚，再决定采集深度”。

把这两篇放一起看，你会更容易建立一个成熟判断：**Agent tracing 的目标不是调试时临时看两眼，而是把一次 Agent 运行变成有边界的工程对象。** 这个对象要能回答四类问题：它是什么工作流、做了哪些子步骤、每一步耗了多少时间和 token、出了问题该去哪里定位。

## Chinese deep summary

如果把今天这两篇材料压成一句话，就是：

**真正进入工程阶段的 Agent，必须先做到“执行链路可见”，然后才谈“策略优化可控”。**

第一层，trace 是 Agent 时代的新“系统调用链”。

你过去做后端和系统集成时，一条请求链路大致是：入口请求、鉴权、业务处理、下游接口、数据库、消息队列、返回结果。现在换成 Agent，链路结构变成了：用户输入、agent 决策、模型生成、工具调用、guardrail、handoff、二次生成、最终输出。表面上对象变了，本质上还是那件事：系统不是因为“某一步存在”就可维护，而是因为每一步都能被命名、计时、串联、归因，才可维护。

OpenAI Agents SDK 文档最值得你建立的意识是：别把 tracing 当成“以后再接”的可选件。它默认就包了 `run -> agent -> generation -> function -> guardrail -> handoff` 这条骨架，说明官方已经把这件事视为 Agent runtime 的基础设施，而不是外围调试功能。对你来说，这很重要，因为它会改变你写 Agent 代码时的视角。你不再只是考虑“能跑通吗”，而会开始考虑“这一步将来出了问题时，能不能从 trace 上一眼看出卡在哪里”。

第二层，观测数据如果没有统一字段，就很难沉淀成组织能力。

很多团队一开始也会“记日志”，但一旦系统变复杂，很快就会遇到两个问题：

- 同样是模型调用，不同服务记的字段名完全不一样。
- 同样是工具调用，有的只记原始 JSON，有的只记耗时，有的什么上下文都没有。

这时 trace 虽然存在，但没法横向分析，也很难做跨项目复用。OpenTelemetry 这篇文章的价值就在这里：它不是只说“要观测”，而是把 GenAI 观测里最关键的对象标准化了，例如模型名、token 用量、结束原因，以及可选的消息和工具调用内容。你可以把它理解成过去你做企业接口集成时的“公共报文头 + 统一日志字段规范”。没有这层约定，团队只能各记各的；有了这层约定，trace 和 metrics 才能进入真正的工程治理。

第三层，Agent 的可观测性不是只为排错，更是为了成本、性能和责任边界。

很多初学者把 trace 理解成“报错时看一眼”。这太窄了。对 Agent 系统来说，trace 至少服务四类任务：

- 性能定位：到底是 LLM 慢，还是某个工具慢，还是 guardrail / handoff 造成了额外回合。
- 成本定位：哪些请求 token 特别高，哪些工作流有明显浪费。
- 行为归因：模型为什么停在 `stop`，为什么停在 `tool_calls`，为什么会连续进入多轮工具执行。
- 责任划分：问题出在模型推理、工具契约、运行时编排，还是外部系统。

这对你尤其关键，因为你未来大概率不是做“一个会聊天的小 demo”，而是做会碰企业系统的 Agent：查工单、读知识库、触发审批、汇总设备告警、生成客户纪要。此时如果没有统一 trace，你就会像过去做现场联调但没有链路日志一样，只能靠猜。Agent 一旦进入 ToB 环境，“靠感觉调 prompt”很快就会撞墙。

第四层，长任务和后台任务的观测要特别小心“写出去了”和“现在看得到”不是一回事。

这点是 OpenAI Agents SDK 文档里最容易被忽略、但最像真实工程问题的部分。默认是 batch export，所以后台任务结束后，trace 可能不是立刻可见。为什么这很重要？因为你一旦开始把 Agent 放进异步 worker、定时任务、后台补偿流程、批量处理链路里，就会自然遇到“任务明明执行完了，为什么平台里还没看到 trace”的排障问题。此时如果你脑子里没有 export/flush 这个概念，就很容易误判成 SDK 丢数据、平台异常，甚至业务逻辑没跑。

这类问题对做过交付的人并不陌生。你会很自然地想到：日志缓冲、批量上报、异步刷盘、链路延迟可见性。这正说明你的旧经验不是包袱，而是迁移优势。Agent 工程里最值钱的人，不一定是最会追新词的人，而是最能把“系统运行证据”设计清楚的人。

第五层，敏感数据采集要默认克制，别把“可观测”做成“全量裸奔”。

这也是今天材料很成熟的一点。OpenTelemetry 博客明确说，默认不抓 prompt 内容和工具参数，只抓模型名、token、时延等元数据；只有你明确开启内容采集，才记录更细内容。这个判断非常像你过去做企业系统时的日志分级和脱敏原则。因为 Agent 的上下文里，经常直接混着客户输入、内部知识、工具实参、返回结果。可观测性做得越强，泄露风险也越高。所以成熟系统不是“先全记下来再说”，而是先区分：

- 哪些字段属于默认安全元数据；
- 哪些字段属于敏感业务内容；
- 哪些字段只允许本地开发阶段短期开启；
- 哪些内容必须脱敏、裁剪或根本不落盘。

你一旦形成这层意识，后面再看 eval、trace、guardrail、MCP 安全，就会发现它们其实不是分散知识点，而是一张完整工程图：**先定义边界，再记录行为，再分析证据，再推动改进。**

## 3 key takeaways

1. Agent tracing 不是调试附件，而是运行时基础设施；如果一次运行没有被拆成 trace 和 span，后续优化、归因和回归验证都会很弱。
2. 只“有日志”还不够，必须有统一语义字段；OpenTelemetry 的 GenAI 约定解决的是跨系统、跨团队、跨工具的可比性问题。
3. 可观测性默认应先采元数据、后采内容；对 prompt、工具参数、工具结果的采集要显式开启并受安全边界约束。

## relation to Agent engineering

这组内容和 Agent engineering 的关系非常直接，因为它补的是“把 Agent 当系统做”这一层，不是补某个单点 API。

对你这种 Java / Spring / 集成 / 交付背景的人来说，最该抓住的不是“我也会看 trace 了”，而是更进一步的判断方式：

- 看到多 Agent / 多工具流程时，先问 span 边界怎么划。
- 看到性能问题时，先问 token、时延、工具耗时有没有分层可见。
- 看到线上反馈时，先问有没有统一字段支持归因和复现。
- 看到要接企业系统时，先问哪些观测数据能落、哪些必须脱敏。

这正是你从“会写几个 Agent demo”走向“能做可上线 Agent 系统”的分水岭。因为企业里的 Agent 工程，最后拼的不是谁会更多新名词，而是谁能把行为链路、成本链路、责任链路都设计清楚。

## a small action for tonight

今晚做一个 30 分钟以内的小练习，不用写大代码，只做“链路拆分”：

1. 选一个你最熟悉的真实场景，比如“设备告警汇总后生成工单建议”。
2. 用 6 到 8 个节点写出它的 Agent 链路：用户输入、检索、模型判断、工具调用、二次生成、人工确认之类。
3. 给每个节点补 3 个字段：`span 名称`、`最该看的耗时/计数`、`最可能暴露的敏感信息`。
4. 最后写一句复盘：`如果这个链路明天上线，我现在最缺的不是提示词，而是哪 2 个观测点？`
