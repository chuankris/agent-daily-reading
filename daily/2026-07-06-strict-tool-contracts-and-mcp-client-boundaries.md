## why read today

你这条转型线前面已经补了不少 Python 工程化、MCP 协议、OAuth、Tracing 和 Spring AI 桥接，现在最容易出现的一个“假进步”是：看起来已经会让模型调工具了，但系统其实还没有形成真正可上线的工具治理能力。

具体会卡在两层：

第一层是“参数契约不够硬”。  
很多 Agent demo 能跑，是因为工具 schema 写得比较松，模型大部分时候也“差不多能猜对”。但一到真实业务，例如查工单、改设备配置、写 CRM 记录、触发审批流，只要参数漏字段、字段名漂移、对象结构多带一层、或把可选项理解错，问题就不是“回答不够好”，而是“流程直接执行错了”。

第二层是“执行边界不够清”。  
就算参数完全合法，也不代表工具调用是安全的。MCP 官方安全文档讲得很直接：本地 server 配置、OAuth 跳转 URL、stdio 启动命令、文件系统和网络权限，这些都是真正的攻击面。也就是说，`schema 对了` 只解决“模型有没有按合同出参”，并没有解决“这次调用该不该被执行、该在什么权限下执行”。

对你这种做过 10 年 Java / Spring / IoT 集成、长期处理 ToB 交付和系统边界的人来说，这两篇材料非常值今天读，因为它们正好把你熟悉的两类工程能力重新映射到 Agent 语境里：

- `strict schema` 对应你熟悉的“接口契约收紧”
- MCP client guardrails 对应你熟悉的“执行面最小权限和显式确认”

换句话说，今天不是再学一个新名词，而是把“能跑 demo”和“能管生产风险”这两件事分开。

## original-text translation

OpenAI 的函数调用文档把一个很多人容易忽略的事实讲清楚了：如果你希望模型产出的工具参数能够稳定落到工程系统里，应该尽量打开 `strict: true`。这样做的目标不是让模型“更聪明”，而是让它更可靠地遵守你给出的函数 schema，而不是像过去那样只做“尽力匹配”。

文档同时明确了严格模式的代价和约束。它不是一句开关，而是一套更严格的 schema discipline：每个对象都要显式写 `additionalProperties: false`，每个 `properties` 里的字段都必须标记为 `required`。如果某个字段在业务上可选，不是靠“省略 required”来表达，而是要把 `null` 放进 type 里。也就是说，严格模式逼着你先把接口边界想清楚，再让模型来调用。

更重要的是，OpenAI 这篇文档其实在提醒你一件工程判断：函数调用不是“模型吐一段 JSON”那么简单，而是“模型在执行一个受约束的远程接口合同”。Responses API 会尽量把 schema 正规化到 strict 模式；如果做不到，就会降级成非严格、尽力而为的调用。对 demo 来说这可能够用，但对要落业务动作的 Agent 来说，你更应该追求“请求直接被拒绝，也不要悄悄放松约束”。

MCP 官方安全文档补上的，是另一半现实。它说得并不抽象，而是非常落地：如果客户端支持一键配置本地 MCP server，那么在真正执行命令之前，必须把完整命令、不截断地展示给用户；必须明确告诉用户，这其实是在本机执行一段潜在危险的代码；必须要求显式确认，并允许取消。这里的核心思想很像你以前做运维平台、设备平台或集成平台时强调的那句话：`不要把“方便”伪装成“安全”`。

文档继续往下推了一层：就算用户确认过，也还不够。MCP 客户端仍然应该高亮危险命令模式，提示敏感目录访问风险，提醒 server 继承客户端权限，并尽量把 server 放进最小默认权限的沙箱里运行。换句话说，MCP 的安全模型不是“用户点过一次同意就完了”，而是“显式知情 + 权限收缩 + 运行隔离”。

如果把这两篇材料放在一起读，你会发现它们其实在讲同一件事的两面：OpenAI 负责把“模型输出”收紧成可信参数，MCP 安全文档负责把“参数落地执行”收紧成可信操作。前者解决“模型有没有按合同说话”，后者解决“系统有没有按边界做事”。

## Chinese deep summary

今天这篇最值得你抓住的，不是单独某个 API 细节，而是一个非常实用的两段式工程框架：

先问：**这次工具调用的参数，是否已经被收紧到足够像正式接口合同？**  
再问：**这次工具调用的执行，是否已经被约束到足够像正式生产变更？**

很多 Agent 初学内容只回答第一个问题的一半，甚至连一半都没答完。大家会讨论 function calling、tool schema、JSON mode、structured output，但默认假设是“只要能解析就能用”。这在你以前做 Java 接口集成时其实是站不住的。你不会因为一段 JSON 能 parse 就认为接口契约是可靠的；你会继续追问：

- 字段是不是固定的
- 是否允许额外字段
- 缺字段时是 reject 还是默默兜底
- 可选语义是“字段可缺失”还是“字段必须出现但值可以为空”
- 一旦调用失败，责任归属是在模型端、网关端还是业务服务端

OpenAI 严格模式文档的价值，就在于它把这些原本散落在后端接口设计里的纪律，重新带回 Agent 工程。`strict: true` 本质上不是提示词技巧，而是“让模型在一份更接近正式 API contract 的约束里工作”。这件事对你尤其重要，因为你并不是要做一个只会聊天的助手，而是大概率会走向：

- 查询知识库并返回结构化结果
- 调内部系统写入工单或客户记录
- 调设备平台查状态、推命令或生成处理建议
- 用多工具编排一个长流程

这些场景一旦参数错了，不会像聊天那样只是“不够优雅”，而是直接变成错误动作、脏数据或者错误审计记录。

但只把参数做严，还不够。MCP 安全文档提醒你：真实风险往往出在工具“执行面”，而不是“描述面”。  
例如：

- 本地 MCP server 的一键安装，本质上是在本机启动一个会继承当前权限的进程
- OAuth 授权 URL 如果校验不严，可能变成 XSS 或命令注入入口
- stdio transport 如果背后连着代理服务和子进程拉起能力，客户端侧漏洞可能被放大成主机级 RCE

这对有系统集成背景的人非常关键，因为你很容易天然理解其中的类比：

- function schema 像接口报文合同
- tool execution 像调用链后的真实操作权限
- strict mode 像服务端强校验
- MCP sandbox / consent / URL validation 像堡垒机、网关、命令审计和最小权限

也就是说，Agent 工程并没有推翻你过去熟悉的工程世界，反而是在要求你把老能力重新摆对位置。  
过去你做 ToB 集成，最怕的是“上游字段漂移 + 下游高权限执行 + 中间没人拦”。  
现在做 Agent，一样最怕：

- 模型参数半对半错
- tool host 默认信任
- 本地或远程 MCP server 拿到过大的文件/网络权限
- 用户没看清楚就点了一键接入

所以今天真正要建立的，不是“我又学会了 strict mode 和 MCP 安全文档”，而是这条判断链：

1. 模型输出必须像正式接口一样被严格约束。
2. 通过约束校验，不等于可以直接执行。
3. 执行前还要经过权限、环境、命令、URL、沙箱和用户确认这层边界治理。
4. 真正成熟的 Agent 系统，靠的是“合同 + 守门”双层机制，而不是“模型今天状态不错”。

你后面如果从 Python Agent demo 走向企业内部助手、运维 Copilot、知识库问答写回、设备运维闭环，这条框架会非常实用。它能帮你在设计时就把问题拆开：哪些属于模型参数问题，哪些属于运行时权限问题，哪些属于平台侧守护责任。这样你不会把所有故障都误判成“提示词没写好”。

## 3 key takeaways

1. `strict: true` 的核心价值不是“更高级的 JSON 输出”，而是把工具参数收紧成更接近正式接口合同的约束体系。
2. 参数合法不等于执行安全；MCP 客户端仍然必须处理显式确认、危险命令提示、URL 校验、沙箱和最小权限。
3. 真正可上线的 Agent 工程，依赖“严格契约 + 执行边界”双层治理，而不是只靠模型在大多数时候猜对参数。

## relation to Agent engineering

这篇内容和 Agent engineering 的关系非常直接，因为它补的是从“会调工具”走到“敢让工具碰真实系统”的关键一段。

第一，它会直接影响你怎么定义 tool schema。  
以后你在 Python 里写工具、在 Pydantic 里建输入模型、或者把 Java/Spring 能力封成 MCP tool 时，不能再只追求“模型大概能懂”。你会更自然地去想：

- 这个字段是不是必须出现
- 能不能接受额外参数
- 可选值到底是缺省还是显式 `null`
- 调用失败时，是 reject 还是自动修补

第二，它会影响你怎么搭 Agent runtime。  
如果一个 runtime 既能调远程 MCP，又能拉起本地 stdio server，那它就不只是“模型适配层”，而是一个真正的执行面。执行面就必须像你以前做集成中台、调度平台那样，有明确的 consent、sandbox、权限边界和审计意识。

第三，它特别适合你的背景迁移。  
你原来强项不是“写几段 Python 花活”，而是“把外部系统接进来还能把边界管住”。这恰好就是 Agent 工程里最稀缺、也最不容易被纯 demo 训练出来的能力。把这两篇文档吃透，相当于把你过去的接口治理、权限治理、环境治理经验，准确迁移到了 tool-calling / MCP runtime 这一层。

## a small action for tonight

今晚做一个 25 分钟的小练习，不写大代码，只做“合同和边界拆分”：

1. 选一个你最可能会做的 Agent 场景，比如“自动汇总设备告警并写工单”或“内部知识库问答后补 CRM 备注”。
2. 先只写 1 个工具的输入 schema，强迫自己把每个字段标成：`必填`、`允许 null`、`禁止额外字段`、`失败时直接拒绝还是提示补全`。
3. 再给这个工具补一张运行时检查清单：`谁能调用`、`调用前是否需要用户确认`、`是否访问本地文件`、`是否访问外网`、`是否需要沙箱`、`是否需要审计日志`。
4. 最后写一句复盘：`如果这个工具今晚就接到生产系统，我更怕参数漂移，还是更怕高权限误执行？为什么？`

## 原文关键段落翻译（人工翻译，放在文末）

1. OpenAI 文档强调：把 `strict` 设为 `true`，可以让函数调用更可靠地遵守函数 schema，而不是只做尽力匹配；官方建议尽量开启严格模式。
2. 严格模式依赖结构化输出能力，因此 schema 也要满足额外约束：每个对象都要设置 `additionalProperties: false`，每个 `properties` 字段都必须标记为 `required`。
3. 如果传入 `strict: true` 但 schema 不满足这些条件，请求会被直接拒绝并返回缺失约束的细节；Responses API 在可能时会尽量规范化到严格模式，否则会退回非严格调用。
4. MCP 安全文档强调：如果客户端支持一键配置本地 MCP server，在执行命令前必须向用户完整展示即将执行的命令，明确提示这是潜在危险操作，要求显式批准，并允许取消。
5. 文档还要求客户端尽量识别危险命令模式、提醒敏感目录访问风险，并让 MCP server 在最小默认权限的沙箱中运行，而不是默认继承宽松宿主权限。
6. 对 OAuth 授权 URL，客户端必须只接受安全 scheme，避免用 shell 命令打开 URL，并对来自 server 的 URL 做严格校验和清洗。
