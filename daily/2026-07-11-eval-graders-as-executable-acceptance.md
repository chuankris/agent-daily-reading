## why read today

你前面已经补过不少“为什么要做 eval”的材料，也已经开始理解 trace、dataset、tool contract、MCP 边界这些概念。现在最该往下走的一步，不是再重复抽象理念，而是把一个很工程的问题想透：

- eval 到底怎么从“感觉这个回答不错”变成“可以自动执行的验收标准”？
- grader 到底是一个抽象评分器，还是 Agent 时代的测试断言？
- 当你以后做企业 Agent，上线后的回归验证，究竟应该靠人肉看几条样例，还是靠一套结构化 grader 持续跑？

这正好卡在你当前阶段的关键缺口上。你原来做 Java / Spring / IoT 集成 / ToB 交付，最熟的不是“把一个 demo 跑起来”，而是定义验收口径、对齐接口契约、沉淀回归测试、避免同类问题反复上线。Agent 工程真正需要迁移的，恰恰就是这套习惯。

今天这两篇官方文档放在一起读，价值很高：

- `Working with evals` 讲的是：一个 eval 不是一句空话，而是 `data_source_config + testing_criteria + dataset` 这种明确结构。
- `Graders` 讲的是：不同 grader 该怎么选，什么时候用精确匹配，什么时候用语义相似，什么时候该上 model grader，什么时候甚至该写 Python grader。

也就是说，第一篇回答“验收标准的骨架怎么搭”，第二篇回答“裁判规则该怎么写得既稳又可维护”。

## original-text translation

`Working with evals` 这篇文档最值得先抓住的一点，是它把 eval 说成了一个非常“后端工程化”的对象，而不是一段主观评语。文档里的例子很直白：先定义一份数据集 schema，告诉系统每个样本里有哪些字段；再定义 `testing_criteria`，明确系统该拿什么输入做判断、和哪一个真值字段比较、使用哪种 grader；最后再把 prompt 放进这套结构里跑。这里最重要的信号是，**eval 的中心不是 prompt，而是被结构化定义出来的“期望行为”**。prompt 只是被拿来接受检验的实现之一。

它还强调了两件很工程的细节。第一，测试数据必须能代表你真实要面对的数据分布，而不是随手拼几条看起来像样的例子。第二，`testing_criteria` 里出现的 `{{ item.xxx }}` 和 `{{ sample.xxx }}` 模板变量，本质上就是把“真值数据”和“模型输出”明确接线。换句话说，eval 不是让模型自己解释自己做得好不好，而是让你提前把判定关系写清楚。

`Graders` 这篇文档则进一步把“裁判规则”拆开了。它给出的信号很明确：**不是所有问题都该直接丢给一个 LLM 裁判。** 如果输出就是固定字符串，就先用 `string_check`；如果工具调用需要校验函数名和参数，可以把多个简单 grader 组合成 `multi` grader；如果参数存在语义等价但文本不完全相同的问题，可以考虑 `text_similarity` 或 `score_model`；如果你已经很清楚业务规则，甚至可以直接写 Python grader。文档其实在提醒你，grader 设计的目标不是“高级”，而是“最小但足够可靠”。

更关键的是，官方还专门提醒了 model grader prompt 也需要被 eval。也就是说，**grader 自己也不是天然可信的**。你需要给 grader 准备高质量样本和人工定过的分数，验证它能不能把好答案和坏答案稳定地区分开。文档甚至直接点出 `grader hacking` 风险：如果一个模型学会了迎合 grader 的漏洞，它可能在 grader eval 里得高分，但在人类专家那里仍然表现很差。

把这两篇合起来，你会更容易建立一个成熟判断：在 Agent 工程里，grader 最像的不是“AI 评分器”，而是“可以持续执行的验收断言层”。它既连接真实业务样本，也约束后续 prompt、tool use、workflow 修改能否安全上线。

## Chinese deep summary

如果把今天的内容压成一句话，就是：

**在 Agent 工程里，grader 不是锦上添花的评分插件，而是把业务验收标准编码成可重复执行回归检查的那一层。**

第一层，eval 的本质是“先定义行为，再测试实现”。

这和你过去做 Java 接口、设备联调、项目交付时的习惯其实非常一致。成熟团队不会说“这个接口看起来差不多能用”，而是会先定义输入、输出、错误码、验收样例，再让实现去满足它。`Working with evals` 文档里最重要的不是 API 细节，而是这种顺序：先定义 `data_source_config`，明确测试样本长什么样；再定义 `testing_criteria`，明确怎么判通过；再上传代表性数据集；最后才让 prompt 或 workflow 去跑。  
这意味着你以后看 Agent 系统，脑子里要先问的不是“模型写得聪不聪明”，而是“通过标准有没有先被结构化写下来”。

第二层，grader 设计应该像写测试断言，而不是像写万能裁判。

很多人第一次接触 eval，会下意识觉得 grader 越智能越好，最好一个 LLM 裁判能解决所有问题。官方文档给出的方向刚好相反：如果能精确匹配，就先精确匹配；如果能拆成两个小判断，就不要上一个大而泛的主观评分；如果工具调用能分别验证函数名和参数，就把它拆开组合。  
这套思路非常适合你，因为它和你熟悉的后端测试哲学是一致的：优先写稳定断言，必要时才引入更复杂的语义判断。对 Agent 来说，这样做还有一个额外好处：当测试失败时，你更容易知道失败在“工具名错了”“参数错了”“语义近似但没满足约束”还是“整体回答方向错了”。

第三层，dataset 不是装饰品，它决定你的 grader 是否真的有生产价值。

文档强调测试数据应该代表真实场景，这一点必须认真看。很多 Agent 评估失败，不是因为 grader 不会写，而是因为样本太像课堂题，不像线上请求。对你这种做过 ToB 交付的人来说，这几乎可以直接翻译成熟悉的话：验收案例如果不接近真实工单、真实告警、真实客户提问，再漂亮的测试也挡不住上线翻车。  
所以你以后沉淀 eval，不要只保存“最标准答案”的样例，而要刻意留住那些脏数据、歧义数据、边界输入、工具参数容易出错的样例。真正有价值的 grader，永远建立在真实失败模式之上。

第四层，model grader 也是要被测试的“代码”。

这是今天最容易被忽略、但也最像工程思维的一点。很多人会把 LLM grader 当成上帝视角，仿佛只要 prompt 写得像模像样，它就天然公正。官方明确反过来说：你得给 grader prompt 准备任务说明、模型或专家答案、以及对应真值分数，然后验证 grader 能否稳定区分好坏。  
这和你过去做规则引擎、告警策略、数据映射脚本很像。不是“写出来就算完”，而是“策略本身也要被验证”。如果一个 grader 自己不稳，那它后面驱动的自动优化、prompt 调整、版本比较，全都会漂。

第五层，`grader hacking` 提醒你，评估系统本身也有攻击面和盲点。

这点特别值得你这种未来可能做企业 Agent 的人重视。Agent 一旦进入持续优化循环，模型和 workflow 都可能逐渐学会“怎样在 grader 里拿分”，却不一定真的对用户更有用。文档给出的识别方式很朴素也很可靠：把 model grader 的判断和人工专家评估交叉对照。如果 grader 分数越来越高，但人工认可度没同步上升，那大概率不是系统真的变好了，而是裁判标准被钻空子了。  
从工程角度看，这意味着评估体系不能只有一条线。你至少要保留人工抽检、代表性高价值样本复看，以及线上 trace 反查能力。Agent 工程不是把人从闭环里彻底拿掉，而是把人的判断放到更高价值的位置。

第六层，Python grader 对你是一个很好的桥梁点。

你当前正在补 Python / Agent / Eval 缺口，而 Python grader 恰好能把你熟悉的“规则判定”思路迁过来。很多业务问题其实不需要一上来就写 LLM grader，比如：

- 工具返回的 JSON 是否包含必须字段
- 输出里的数值范围是否合规
- 某一步结果是否满足前后约束
- 某些字段是否与输入中的实体保持一致

这类规则用 Python grader 往往比纯 prompt grader 更稳、更便宜、更容易回归。对你来说，这会是一个非常现实的过渡路线：先把你擅长的显式规则判断迁移过来，再逐步引入 model grader 处理语义性更强的部分。

## 3 key takeaways

1. 一个有用的 eval 不是“写个 prompt 看效果”，而是先定义数据 schema、测试准则和代表性样本，再让 prompt 或 workflow 接受检验。
2. grader 的首要目标不是智能，而是稳定；能用 `string_check`、`multi`、Python 规则解决的问题，不要过早交给泛化的 model grader。
3. model grader 自己也必须被评估；如果只看 grader 分数、不做人工交叉验证，就会有 `grader hacking` 风险。

## relation to Agent engineering

这组内容和 Agent engineering 的关系非常直接，因为它补的是“怎么把 Agent 改动纳入可控回归体系”这一层。

对你这种 Java / Spring / 系统集成 / 客户交付背景的人来说，最该迁移过来的不是某个 Python 语法点，而是下面这套判断顺序：

- 先把业务成功标准写成结构化判定，再讨论 prompt 怎么调。
- 先让工具调用、参数、输出格式变得可判定，再讨论模型是不是更聪明。
- 先保留代表性失败样本和人工真值，再讨论自动优化闭环。

这会直接影响你以后怎么设计 Agent 系统：

- 你会更自然地把 tool calling 看成“可断言行为”，而不是黑盒魔法。
- 你会更自然地把 eval dataset 看成“回归资产”，而不是演示素材。
- 你会更自然地把 grader 分成规则层、语义层、人工复核层，而不是只追求一个万能总分。

这正是从“会做 Agent demo”走向“能维护上线 Agent 系统”的分水岭。

## 原文关键段落翻译（人工翻译，放在文末）

1. `Working with evals` 的核心意思是：运行一个 eval，需要一份能代表真实输入分布的测试数据集；在 `data_source_config` 里，你要先定义每条数据的结构，再让后续评估围绕这个结构展开。
2. 同一篇文档还强调：`testing_criteria` 定义的是“如何判断模型输出是否满足要求”；其中 `item` 指向数据集里的真值字段，`sample` 指向模型生成出的结果，评估逻辑就是在两者之间建立明确比较。
3. `Graders` 文档在工具调用场景给出的建议是：可以把函数名检查和参数检查拆成两个 grader，再用 `multi` 组合；这样比分不清责任的大 grader 更容易维护。
4. 对参数判断，官方特别提醒：如果只是文本略有差异但语义等价，精确字符串匹配可能会误伤，这时更适合用 `text_similarity` 或 `score_model` 去看语义相近程度。
5. 对 model grader，官方明确说它的 prompt 也要迭代评估；你需要准备详细任务说明、高质量答案样本，以及对应真值分数，用来验证 grader 是否真的能把好坏答案区分开。
6. 文档还提醒了 `grader hacking` 风险：被训练的模型可能学会钻 grader 的漏洞，导致它在 grader eval 里分数很高，但在人类专家那里表现依然很差。
7. `Graders` 还给出了一条很实用的路线：如果你的判断逻辑本来就清楚、规则也能显式写出，那直接用 Python grader 执行代码评分，往往会比把问题全交给 LLM 更稳。
